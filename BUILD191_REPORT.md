# BUILD191 REPORT — full-game audit + multiplayer reliability pass (2026-09-24)

Owner ask: *"multiplayer kind of works, kind of doesn't — difficult to get into a match and keep it reliable … find any slight, critical or crucial issues."* Constraint: no Lovable credits for 5 days → every fix is client-side.

## How it was done
- **Audit:** 7 lens finders (MP entry, MP match, MP transport/identity, tournaments/co-op/chat, engine, data/network, UI) over build190, each finding re-traced by an adversarial verifier told to refute it. 61 kept, 1 refuted.
- **Live proof:** a two-peer harness — two guest browsers on separate origins against the REAL production Supabase Realtime — reproduced the complaint: **4 of 7 match starts failed** (host start-watchdog false abort → guest played alone, host ran a "zombie" solo round).
- **Fix:** 5 implementation batches + 2 adversarial code reviews (12 regressions caught and fixed before shipping) + 3 live harness passes. Final pass: every scenario green.

## Live results (two real peers, real Supabase Realtime)
| Scenario | build190 | build191 |
|---|---|---|
| Room / quick-match START on 3–4 min tracks | 3/5 (+ CPU warm-ups aborting) | 6/6, then 4/4 — zero aborts; guest uses the host chart |
| PLAY NOW pairing (simultaneous, staggered, tap-before-connected) | 2/3 (tap-before-connected → false "Sign in") | 4/4 + 1/1 |
| Guest reload mid-match | stranded silently in the lobby | visible card → re-seated when the match ends |
| REMATCH after the opponent re-enters | deadlock | 3/3 (+ variant 1/1) |
| Host reload | room came back PRIVATE, renamed, combat lost | original name/privacy/combat kept |
| Leave via Esc / Back | ghost seat left behind | opponent sees LEFT in ~0.2s |
| CPU warm-up | aborted → zombie run | starts cleanly |

**Not provable headless:** 60fps feel, the desktop split-screen, and signed-in-only paths (battle-call ring, room codes) — please test those on your machine.
